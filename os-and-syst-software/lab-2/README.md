Разобраться, из каких сегментов состоит виртуальное адресное пространство процесса

## Этап 1. Карта памяти

```
$ ./lab2 1
PID:            844
.data (global_init): 0x55a093819078
.bss  (global_uninit): 0x55a0938190ac
heap  (malloc(100)):  0x55a0b3d40010
stack (local):        0x7ffee3845e8c
.text (main):         0x55a093816588
```

Пока программа ждала Enter, во втором терминале был открыт `/proc/844/maps`
(оставлены только нужные строки):

```
55a093815000-55a093816000 r--p 00000000 /root/lab2/lab2
55a093816000-55a093817000 r-xp 00001000 /root/lab2/lab2   ← main
55a093817000-55a093818000 r--p 00002000 /root/lab2/lab2
55a093818000-55a093819000 r--p 00002000 /root/lab2/lab2
55a093819000-55a09381a000 rw-p 00003000 /root/lab2/lab2   ← global_init, global_uninit
55a0b3d40000-55a0b3d61000 rw-p 00000000 [heap]            ← malloc
7ffee3826000-7ffee3847000 rw-p 00000000 [stack]           ← local
```

Порядок адресов от меньшего к большему: `.text` → `.data` → `.bss` → heap →
библиотеки (mmap) → stack. Это ровно схема из раздела 2.1: код и статические
данные лежат в самом низком сегменте образа, куча растёт вверх сразу за `.bss`,
а стек — в самом верху адресного пространства и растёт вниз.

Каждый адрес попал в свою строку `maps`, то есть это реальные адреса процесса, а
не абстракция: `local` — в `[stack]`, `malloc` — в `[heap]`, `main` — в сегменте
`r-xp` самого бинарника.

## Этап 2. Рост стека и переполнение

```
$ ulimit -s
8192
$ ./lab2 2 | tail -n 3
depth =  7818, &buffer[0] = 0x7fff958442b0
depth =  7819, &buffer[0] = 0x7fff95843e80
depth =  7820, &buffer[0] = 0x7fff95843a50
Segmentation fault (core dumped)
```

Рекурсия упала на глубине **7820**. Адреса `buffer` от шага к шагу уменьшаются
на `0x430` = **1072 байта**: 1024 байта самого массива плюс ~48 байт служебного
фрейма (сохранённый `rbp`, адрес возврата, выравнивание). Уменьшение адресов
подтверждает, что стек растёт вниз.

Оценка «размер стека / размер фрейма»: 8192 КБ / 1072 Б ≈ 7823 кадра — совпадает
с практикой. В повторных запусках глубина получалась 7816…7820: вершина стека
рандомизируется ASLR с точностью до страницы (4096 Б ≈ 3.8 кадра), плюс часть
стека занята аргументами и переменными окружения.

Проверка линейной зависимости — тот же запуск с уменьшенным стеком:

```
$ (ulimit -s 1024; ./lab2 2 | tail -n 1)
depth =   971, &buffer[0] = 0x7fff1a7caa30
```

1 МБ / 1072 Б ≈ 977 — тоже сходится. Про `-Wall`: компилятор предупреждает
`-Winfinite-recursion`, и для этого этапа это ожидаемо — рекурсию останавливает
только переполнение стека.

Причина падения: стек — ограниченная
область (8 МБ по умолчанию), и когда очередной фрейм выходит за её нижнюю
границу, процессор обращается к неотображённой странице, ядро доставляет
SIGSEGV, и программа аварийно завершается (код 139).

## Этап 3. «Сырая» память и Little-Endian

```
$ ./lab2 3
x = 0x41424344, sizeof(x) = 4
байт 0: адрес 0x7ffcf8d3ad74  hex 44  символ 'D'
байт 1: адрес 0x7ffcf8d3ad75  hex 43  символ 'C'
байт 2: адрес 0x7ffcf8d3ad76  hex 42  символ 'B'
байт 3: адрес 0x7ffcf8d3ad77  hex 41  символ 'A'
```

Байты идут `44 43 42 41`, то есть младший байт числа (`0x44`, символ `D`) лежит
по младшему адресу — система **Little-Endian**. Приведение `(unsigned char *)&x`
заставляет смотреть на одно и то же место памяти как на массив из 4 байт:
тип в C — только «маска» над байтами, а не свойство самой памяти.

```

==872==     in use at exit: 40 bytes in 1 blocks
==872==   total heap usage: 2 allocs, 1 frees, 4,136 bytes allocated
==872==
==872== 40 bytes in 1 blocks are definitely lost in loss record 1 of 1
==872==    at 0x48658A8: malloc (vg_replace_malloc.c:446)
==872==    by 0x40014DD: stage4 (lab2.c:95)
==872==    by 0x4001630: main (lab2.c:130)

`40 bytes` — это ровно `10 * sizeof(int)`. Valgrind не только нашёл утечку, но и
показал строку `malloc` (спасибо сборке с `-g`).

==878==

==878== ERROR SUMMARY: 0 errors from 0 contexts
```

Второе выделение в куче — внутренний буфер `printf`, его освобождает сама libc.

## Этап 5. Карта памяти и ASLR

Права сегментов объясняются их содержимым:

| Сегмент | Права | Почему |
|---|---|---|
| `.text` | `r-xp` | код нужно читать и исполнять, но нельзя менять — иначе программа могла бы переписать сама себя |
| `.data` / `.bss` | `rw-p` | переменные меняются во время работы, но исполнять их не нужно (W^X) |
| `[heap]` | `rw-p` | данные `malloc`, тоже только чтение/запись |
| `[stack]` | `rw-p` | локальные переменные; стеку не нужен `x` — это защита от переполнения буфера с переходом на свой же код |

Пять запусков подряд:

| Запуск | `.text (main)` | `heap` | `stack` |
|---|---|---|---|
| 1 | `0x560f522cb588` | `0x560f53ea9010` | `0x7ffd378ecffc` |
| 2 | `0x555868dd4588` | `0x55588d908010` | `0x7ffe1e76971c` |
| 3 | `0x559994a24588` | `0x5599c1649010` | `0x7ffdb8ffb38c` |
| `setarch -R` #1 | `0x555555555588` | `0x555555559010` | `0x7fffffffea4c` |
| `setarch -R` #2 | `0x555555555588` | `0x555555559010` | `0x7fffffffea4c` |

С ASLR база образа (`.text`/`.data`), куча и стек каждый раз разные, но **внутри
одного запуска** смещения постоянны: `main` всегда на `+0x2af0` от начала
`.data`, а `heap` — сразу за `.bss`. С `setarch -R` (отключение рандомизации)
адреса становятся фиксированными: PIE-образ грузится по `0x555555554000`, стек —
по `0x7ffffff...`. Видно и то, что при отключённом ASLR куча примыкает к
бинарнику (`0x555555559010`), а при включённом она отодвинута на мегабайты —
это brk-рандомизация.

## Контрольные вопросы

**1. Почему в Java нет Segmentation Fault, а в C есть?** JVM — прослойка: байт-код
исполняется виртуальной машиной, которая сама проверяет границы массивов,
типы ссылок и null, и при ошибке бросает исключение (`NullPointerException`,
`ArrayIndexOutOfBoundsException`). В C программа работает с адресами напрямую,
проверок нет — обращение по неверному адресу уходит в MMU и превращается в
SIGSEGV.

**2. Что будет, если функция вернёт адрес локальной переменной?** Её фрейм
уничтожается при возврате, и адрес указывает на уже освобождённую (или
переиспользованную) область стека — это *dangling pointer*. Читать через него
нельзя: значение может быть затёрто следующим вызовом, а запись испортит чужие
данные. Компилятор предупреждает `-Wreturn-local-addr`.

**3. Зачем `malloc`, если есть массивы в стеке?** Стековые массивы живут только
до конца функции и ограничены 8 МБ, а их размер должен быть известен на этапе
компиляции. `malloc` даёт память, которая живёт сколько нужно (до `free`),
размер задаётся во время выполнения, а большой массив не рискует переполнить
стек.

**4. Как искать утечку в работающей системе?** Смотреть рост RSS у процесса:
`top`/`ps`, затем `pmap <PID>` и `/proc/<PID>/smaps` — какие области растут.
Valgrind для продакшена неудобен: он замедляет программу в 10–50 раз, требует
отладочных символов и перезапуска под собой. Поэтому используют eBPF/heaptrack,
`malloc`-хуки, `LD_PRELOAD`-профайлеры и метрики памяти сервиса.

**5. Почему адреса различаются между запусками и как это влияет на
безопасность?** ASLR случайно сдвигает базу образа, кучу, стек и библиотеки при
каждом запуске. Атакующему труднее предсказать адрес функции или буфера, а
значит, сложнее подставить нужный адрес в эксплойт (ret2libc, ROP). Это не
защита от ошибок, а усложнение эксплуатации; вместе с NX и stack canary она
заметно поднимает планку.

## Выводы

* Адреса реальных переменных точно соответствуют схеме сегментов и строкам
  `/proc/<PID>/maps`: `.text` внизу, за ним `.data`/`.bss`, выше куча, стек — в
  самом верху и растёт вниз.
* Стек ограничен 8 МБ; рекурсия с 1 КБ на кадр падает примерно на 7820-м уровне,
  а при `ulimit -s 1024` — около 971-го, то есть зависимость линейная.
* Порядок байт в памяти — Little-Endian; приведение указателя позволяет читать
  число как массив байт.
* `malloc` без `free` — утечка, которую Valgrind находит с точностью до строки;
  после `free` отчёт чистый.
* ASLR рандомизирует абсолютные адреса, но относительное расположение сегментов
  внутри процесса сохраняется.

## Как запустить

```bash
gcc -g -O0 -Wall src/lab2.c -o lab2
./lab2 1                 # карта памяти, ждёт Enter для /proc/<PID>/maps
./lab2 2 | tail -n 3     # рост стека до Segmentation Fault
./lab2 3                 # Little-Endian
valgrind --leak-check=full ./lab2 4          # утечка
valgrind --leak-check=full ./lab2 4 fixed    # без утечки
setarch $(uname -m) -R ./lab2 1              # без ASLR
```
